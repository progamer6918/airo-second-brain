## Source-derived module — Batch01  Supervisory Monitoring To Corrective Action
_Reconstruction module: `B01` / `BATCH01__SUPERVISORY_MONITORING_TO_CORRECTIVE_ACTION.md`_

## Scope

This compiled module uses only these four source-grounded dossiers:

1. `2. ASSDP Basic - PDCA.pptx`
2. `10. Sales _ Stock Monitoring per Dealer.pptx`
3. `11. Analisa Pricing _ FID-BA.pptx`
4. `12. PICA.pptx`

It is an early WorkDesk module, not a complete Dealer Performance domain. It deliberately leaves forecasting formulas, Dealer Review workbook logic, demand/recovery, NOS, CRM, and current 2026 operating standards for later sources.

## The operating chain

The four sources form a coherent management chain:

`PLAN → EXECUTE & OBSERVE → LOCALIZE PERFORMANCE GAP → TEST CAUSE → CORRECT → RE-MONITOR`

More concretely:

1. **Plan** — forecast market/sales, set targets, determine strategy/activity, plan supervision.
2. **Execute & observe** — monitor sales/stock, programs, competitors, policy execution, and field conditions.
3. **Localize** — move from Total MD to Kabupaten to Dealer to Series, or from Product/Segment to Area to Dealer.
4. **Diagnose** — combine contribution analysis with evidence about market, competitor, stock, Honda programs, price/financing, etc.
5. **Causal quality check** — ask whether the explanation changed when the symptom changed, whether it explains differential behavior, and whether its magnitude is sufficient.
6. **Correct** — build PICA/countermeasure specifically against the validated mechanism.
7. **Control** — monitor the resulting achievement and market share, then continue PDCA.

This synthesis is not stated verbatim in one slide; it is a cross-source relationship supported by the four decks.

## Layer 1 — Supervisory control system

From PDCA, the Area Supervisor is expected to connect planning, execution control, performance review, and corrective action. The work is multi-cadence and multi-evidence:

- Target/plan.
- Daily sales and stock.
- Weekly/monthly achievement.
- Market share.
- Competitor programs/activities.
- Dealer Review dimensions.
- Field supervision.
- Financial-company information.

WorkDesk implication: **a Dealer problem should not be analyzed from one KPI in isolation.**

## Layer 2 — Monitoring hierarchy

Sales & Stock Monitoring supplies the primary localization structure:

`Total MD → Kabupaten → Dealer → Series`

The data basis is explicitly `M vs M-1` daily sales/stock movement. At total-MD level, Sales is read together with Stock MD, Stock Dealer, AHM–MD in-transit, and AHM Distribution. The purpose is not merely to find a red number; it is to locate where movement comes from and whether inventory flow may be relevant.

## Layer 3 — Flexible decomposition path

PICA generalizes localization into two paths:

### Area-led symptom
`Main Dealer → Kabupaten → Dealer → Type`

### Product-led symptom
`Main Dealer → Segment/Type → Kabupaten → Dealer`

This creates a WorkDesk routing rule:

- If the initial question is **“which area/dealer is causing the gap?”**, start Area→Product.
- If the initial question is **“which product/segment is causing the gap?”**, start Product→Area.

That routing is a synthesis of the two PICA funnels, not a separate AHM policy statement.

## Layer 4 — Root-cause evidence families available in Batch 01

The sources explicitly mention the following candidate evidence families:

### Market / external
- Market information.
- Commodity prices.
- Weather/natural disaster.
- Political/social/environmental conditions.
- Economic drivers.

### Competitive
- Competitor sales program.
- Competitor price/discount/DP/installment.
- Promotion / BTL / GC.
- Competitor stock.

### Honda internal/execution
- Honda sales program changes.
- Honda BTL/activity changes.
- Stock / short stock / fulfillment.
- AHM/MD strategy execution by Dealer.
- Dealer Review dimensions.

### Financing
- Fincoy package competitiveness.
- DP layer.
- FID/BA4 trend and financing quality.
- Consumer occupation/SES segmentation.

Important: these are **candidate evidence families**, not automatic causes.

## Layer 5 — Causal quality gate

The PICA deck provides a reusable quality standard that should be embedded in WorkDesk diagnostics.

Before accepting a root cause, ask:

1. **Change test** — what changed versus the comparison period?
2. **Contrast test** — if the proposed cause is broad, why did other comparable products/areas not move the same way?
3. **Magnitude test** — is the proposed factor quantitatively large enough to explain the observed gap?
4. **Mechanism test** — how does the factor logically produce the observed sales/M/S effect?
5. **Localization test** — does the cause occur where the performance contribution is actually concentrated?
6. **Actionability test** — can corrective action be linked directly to the identified mechanism?

Only tests 1–3 are directly illustrated/questioned by PICA; tests 4–6 are WorkDesk synthesis consistent with the examples and PDCA action logic.

## Layer 6 — Pricing and financing branch

Pricing/FID-BA adds a specific diagnostic branch when sales or market share may be commercially constrained.

### Price competitiveness branch

Compare head-to-head:

- OTR.
- DP Pricelist.
- Discount.
- DP Real.
- Installment.
- Credit rate.

A package can be uncompetitive even when OTR is competitive.

### Financing-quality branch

If FID/BA4 is high or worsening, financing companies may become more selective. Therefore a sales gap may reflect not only demand/price but **credit-access tightening** by product/customer/area/Dealer.

This branch must be treated with lender-specific and time-specific caution because thresholds/policies in the source are 2023 training data.

## Batch-01 diagnostic routing model

When a user asks, for example, “Retail turun, kenapa?”, WorkDesk should not jump immediately to a cause. A source-grounded sequence is:

1. Confirm exact symptom: Retail? Daily Sales? M/S? which period?
2. Read total movement and comparison basis.
3. Localize by Area/Kabupaten/Dealer/Series or Segment/Type/Area.
4. Check sales together with stock/in-transit/distribution where available.
5. Identify major negative/positive anomalies.
6. Gather evidence from market, competitor, Honda execution/program, stock, and commercial/financing branches.
7. Run causal quality questions: changed? differential? magnitude?
8. Form explicit Problem Identification.
9. Define Corrective Action that addresses the mechanism.
10. Define next action/control and re-monitor under PDCA.

## Source-derived module — Practical Problem Solving And Negotiation
_Reconstruction module: `B07` / `PRACTICAL_PROBLEM_SOLVING_AND_NEGOTIATION.md`_

## Two different jobs

Problem solving determines **what should be changed**. Negotiation/influence helps secure **agreement/resources/behavior needed to execute the change**.

Do not mix them:
- A weak diagnosis cannot be fixed by better persuasion.
- A correct diagnosis can still fail if stakeholders do not agree to act.

## PPS flow

`actual-vs-desired gap -> breakdown/Pareto -> facts/data -> hypotheses -> test -> 5 Whys -> root cause -> temporary + real solution -> PIC/due/status`.

## Negotiation preparation

Before asking for dealer/partner commitment define:
- BATNA;
- reservation value;
- aspiration;
- likely ZOPA.

Then select an influence approach supported by the training source: social proof, liking, contrast, time-machine/future visualization, higher purpose.

## Application to dealer supervision

Example:
- Diagnosis says a dealer needs additional weekend activity and dedicated follow-up capacity.
- PPS establishes why and how much.
- Negotiation prepares what minimum commitment is acceptable, what alternative exists if the dealer refuses, and how to frame the business benefit.

The result should be a negotiated operational commitment, not a motivational speech detached from evidence.

## Source-derived module — Human Centered Innovation Design Thinking
_Reconstruction module: `B07` / `HUMAN_CENTERED_INNOVATION_DESIGN_THINKING.md`_

## When to use

Use when the problem is not solved by simply enforcing a known standard; especially when customer behavior, experience or unmet needs are uncertain.

## Source flow

1. **Explore** - immerse, observe, engage.
2. **Identify** - synthesize user, need and insight.
3. **Ideate** - generate many possible solutions; use HMW.
4. **Visualize** - prototype the experience at sufficient fidelity to learn.
5. **Evaluate** - test with real users, observe behavior and gather unmet needs.

The source explicitly treats the process as non-linear.

## Key discipline

- Empathy is evidence gathering, not guessing what customers feel.
- Insight is not a demographic description; it explains the underlying reason/need.
- Ideation should delay premature filtering.
- Prototype to learn, not to defend an idea.
- Evaluation asks what the user accepted and what remains unmet.

## Link to WorkDesk

Design thinking complements PICA/PPS:
- PPS is strongest when the desired state and operational failure can be decomposed.
- Design thinking is strongest when the desired customer solution itself is still uncertain.

They can be sequential: PPS isolates a customer-experience problem, Design Thinking explores a new solution, then PPS/PDCA governs execution and correction.

## Source-derived module — Business Case Engineering
_Reconstruction module: `B07` / `BUSINESS_CASE_ENGINEERING.md`_

## Required logic

The combined sources define a business case as more than an Excel forecast:

1. **Market Insight** - why the problem/opportunity exists.
2. **Breakdown Target** - what result is required and how it decomposes.
3. **Excellent Execution** - what strategy/activity will be executed and monitored.
4. **Economics** - budget/cost and expected profit or benefit.
5. **Evidence** - before/after and field-monitoring proof.
6. **Customer/CRM linkage** - where relevant, connect the strategy to actual customer data/needs/leads.

## Anti-patterns

- numbers with no new strategy;
- activity list with no market problem;
- target with no ownership/coverage;
- budget with no expected benefit;
- "customer focus" with no CDB/need evidence;
- before/after without explaining causal mechanism;
- one-dealer anecdote presented as area strategy.

## Training-case workbook role

The workbook intentionally leaves future targets/activity blank. It is a thinking scaffold, not a hidden answer key.

## Source-derived module — Market Insight To Excellent Execution
_Reconstruction module: `B07` / `MARKET_INSIGHT_TO_EXCELLENT_EXECUTION.md`_

## The intermediate-level supervisory chain

`market/customer insight -> target logic -> network/dealer/people deployment -> exact activity/program/product -> monitoring -> adaptation`.

### Market insight
Use market size, M/S, Honda sales, economic drivers, customer/CDB, product segmentation and people capacity.

### Target
Break down:
`MD/area -> kabupaten -> dealer -> sales people -> series/type`.

A target is incomplete until ownership and coverage are clear.

### Resource
Calculate people, budget and planning/forecasting needs. Allocate roles according to strengths and role requirements.

### Excellent execution
Specify:
- exact place;
- exact product;
- exact customer;
- exact program;
- exact PIC;
- exact timing;
- monitoring metric.

### Adaptation
Monitor performance and market response; change execution when evidence changes.

## "Doctor for dealer" rule

Do not carry raw data into a dealer meeting and call it analysis. Convert data to information, connect it to context, diagnose, and propose treatment.

## Source-derived module — Advance Methods Dmaic Pica Pdca Design Thinking
_Reconstruction module: `B08` / `ADVANCE_METHODS_DMAIC_PICA_PDCA_DESIGN_THINKING.md`_

ASSDP Advance explicitly permits multiple project methods. WorkDesk should choose method based on the problem, not force every task into one template.

| Method | Best fit | Core question |
|---|---|---|
| PICA | Operational performance gap requiring decomposition/corrective action | Where is the problem, why, and what corrective action? |
| PDCA | Recurring execution / continuous improvement | Did the plan work and what should be standardized/corrected? |
| DMAIC | Quantified improvement project with baseline, root cause and control | Can we define, measure, analyze, improve and control the gap? |
| Design Thinking | Customer problem/solution uncertainty | What does the user actually need and what solution works? |
| 8 Step | Allowed by Advance project guidance; exact source-specific steps not reconstructed in Batch08 | Use only when a trusted 8-Step reference is available. |

## Combination rule

Methods can nest:
- Design Thinking to discover human need;
- DMAIC/PICA to diagnose measured operational gap;
- PDCA to run and improve ongoing execution.

Do not claim “method complete” when its source-specific process has not yet been reconstructed.

## Source-derived module — Critical Creative Innovation
_Reconstruction module: `B08` / `CRITICAL_CREATIVE_INNOVATION.md`_

## Ambidextrous thinking

The source pairs:
- **critical** -> exploitation / improvement;
- **creative** -> exploration / new possibilities.

Innovation needs both.

Creative without critical screening produces exciting but fragile ideas. Critical without creative exploration optimizes the old system forever.

## Improvement side

Continuous improvement uses PDCA and standardization:
`Plan -> Do -> Check -> Act -> standardize -> improve again`.

## Creative side

Questions:
- WHAT IF?
- “Bagaimana kalau?”

SCAMPER:
- Substitute;
- Combine;
- Adopt/adapt;
- Modify/Magnify;
- Put to other use;
- Eliminate;
- Rearrange/Reverse.

Creative association should borrow mechanisms from other contexts/industries, then adapt rather than copy blindly.

## Critical side

Ask:
- Is the pattern consistent?
- What is the evidence?
- What are the implications?
- Is it rational/realistic?
- What are the facts?
- Why?

Idea selection must explicitly consider applicability and risk.

## Innovation loop

`Problem/opportunity -> expand possibilities -> screen evidence/risk -> prototype/test -> measure -> standardize or discard`.

## Source-derived module — Strategy To Execution And Breakthrough
_Reconstruction module: `B08` / `STRATEGY_TO_EXECUTION_AND_BREAKTHROUGH.md`_

## ASSDP Advance standard

The final-project requirement defines the expected supervisory product:

**Breakthrough Integrated Strategy & Activity to Develop Weak Area into a Strength Area.**

This means “strategy” is not a PowerPoint idea. It must integrate:

`Demand/Market -> Marketing Strategy -> Target -> Execution -> Monitoring -> Evaluation -> Corrective Action -> Next Strategy`.

## Weak-area breakthrough logic

1. **Prove the weak area** - gap, denominator, contribution and benchmark.
2. **Find why it matters** - size/potential, strategic contribution, customer/economic context.
3. **Break the gap down** - area/product/dealer/people/activity/customer/process.
4. **Test root causes** - evidence over narrative.
5. **Set target** - quantified, staged, owned and tied to market assumptions.
6. **Design integrated response** - each intervention should map to a cause.
7. **Use channel/network/digitalization** - not just marketing activity.
8. **Monitor leading + lagging indicators**.
9. **Evaluate effectiveness** - activity completed is not activity effective.
10. **Standardize / scale / redesign** based on evidence.

## PENETRASI example

The Merangin case demonstrates this pattern:
- high-volume market but share below province;
- farmer/community decision context;
- sales dependence on walk-in;
- canvassing + AHASS opportunity;
- three interventions mapped to three root causes;
- daily sales monitoring + monthly market/activity review.

Do not copy the interventions mechanically. Copy the **cause-to-intervention architecture**.

## Breakthrough gate

A proposal is not “breakthrough” merely because it is new. It needs:
- meaningful gap/opportunity;
- different mechanism from business-as-usual;
- explicit hypothesis;
- measurable target;
- evidence during execution;
- control/learning loop.

## Source-derived module — Goal Time And Problem Solving System
_Reconstruction module: `B09` / `GOAL_TIME_AND_PROBLEM_SOLVING_SYSTEM.md`_

## Goal-to-week execution
Role -> goal -> Important/Not Urgent priorities -> Big Rocks -> weekly calendar -> integrity of execution.

Use Urgent/Important classification as an attention tool, not as a mathematical performance score. The aim is to protect work that prevents future problems and builds capability.

## Problem-solving control
A problem is a measurable gap, not a feeling.

`Current State -> Desired State -> Gap`

Then:
1. list competing hypotheses;
2. define what evidence would support/reject each;
3. test before committing to a cause;
4. ask why until reaching a controllable root cause;
5. connect each root cause to action, PIC, due date and status;
6. monitor whether the gap actually closes.

This Basic method is a simpler predecessor/complement to the deeper PPS/PICA/DMAIC methods reconstructed in Batches07-08.

## Source-derived module — Project From Problem To Sustained Improvement
_Reconstruction module: `B09` / `PROJECT_FROM_PROBLEM_TO_SUSTAINED_IMPROVEMENT.md`_

The project guidance, scoring rubric and Owner cases converge on one durable project architecture:

`Issue / business gap`  
`-> evidence & measurement`  
`-> root-cause analysis`  
`-> solution tied to cause`  
`-> implementation in network`  
`-> before/after result`  
`-> standardization`  
`-> monitoring/control`  
`-> clear presentation`.

The 2023 scoring rubric materially rewards implementation and sustainability: **50% implementation + 10% monitoring**, compared with 30% concept and 10% presentation. That weighting is a strong reminder that a professional project is judged by what changed in the operating system, not only by analytical elegance.

Use the aging-stock project as a historical applied case: diagnosis identified FIFO/focus/motivation gaps; treatment combined process, incentives and daily/weekly control; the next step was scale and consistency.
